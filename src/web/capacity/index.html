Polling lifecycle

Turn submission age into a recurring scrape schedule. Enabled stages run in the order shown.

How lifecycle stages create jobs

Every new URL is one submission. While it is in a polling stage, each scheduled poll becomes one logical scrape job. Frequent fresh-stage polling creates many more jobs than the daily arrival count alone suggests.

Stage days × polls per day × submissions/day → recurring jobs/day

A blank interval means the stage is dormant: the submission remains active for retention, but it creates no polling jobs. Disabling a stage removes its days from the lifecycle entirely.

Latency and reliability

Describe how long work stays in flight and how failed attempts turn into retries.

Latency, P95, and eventual success

Mean latency represents normal operation. P95 means 95% of operations complete within that time; the slowest 5% take longer, so P95 is used for peak sizing.

A job may fail its first attempt and still eventually succeed. Retryable failures can make additional attempts; permanent outcomes such as private or not found do not retry.

Workers and peak sizing

Set process-local throughput and in-flight capacity, then describe the peak to plan for.

Throughput is not concurrency

Throughput is work completed over time, such as jobs/minute. Concurrency is work currently in flight. At the same throughput, slower jobs remain in flight longer and therefore need more concurrent slots.

Throughput + latency → jobs in flight → worker slots
Static proxy pool

Describe the capacity of each static proxy so the model can size the pool against its tightest limit.

How static proxy sizing works

The model independently checks job concurrency, HTTP requests/minute, and monthly bandwidth. Whichever needs the most proxies is the binding constraint.

Raw requirement × (1 + safety margin) → round up to recommended proxies

Probation is a cautious starting capacity. Earned concurrency is what warm proxies have actually sustained; neither is a rotating-residential proxy assumption.

How is this calculated?

Workload comes from the configured polling lifecycle, not a fixed scrapes-per-submission input. New submissions form age-based cohorts, and every scheduled poll creates one logical scrape job.

Sustainable capacity is the lowest steady-state ceiling across configured worker and static-proxy constraints. The calculator then inverts the same lifecycle model to find the arrival rate that reaches that ceiling. Peak metrics remain separate because they describe bursts rather than sustainable run rate.

Submission → polling schedule → logical jobs

A submission is one URL entering the model. It is active while it remains in any lifecycle stage, but it is polled only in stages with an interval. Every scheduled poll of one URL creates one logical job.

Jobs/day exceeds submissions/day because the same submission is scraped repeatedly as it ages. The launch workload ramps until every polling age cohort is populated.

Reliability

See how first-attempt failures, permanent outcomes, and retries change eventual success and operational load.

Why eventual success can hide retry traffic

“Eventual job success” counts a job as successful if any allowed attempt succeeds. Attempt amplification counts all expected attempts, including failures before that success. Those extra attempts increase HTTP traffic, bandwidth, and possibly cost.

Logical jobs and HTTP traffic

Translate scheduled URL scrapes into the outbound requests that platform and proxy limits actually see.

Keep these units separate: 1 logical job is one scheduled scrape of one URL. That job can issue multiple HTTP requests, and a retry repeats the job’s HTTP fan-out.
Example: one job is not one request
1 TikTok logical job × 2 HTTP requests/job → 2 baseline HTTP requests

Retry-adjusted traffic then multiplies baseline requests by attempt amplification. Logical jobs remain separate so retry traffic never looks like additional scheduled work.

Bandwidth

HTTP requests × bytes/request → bandwidth
Baseline, retries, month, and horizon

Before-retry bandwidth shows the approved workload baseline. Retry-adjusted bandwidth reflects expected actual traffic and drives capacity and cost. GB here is decimal: 1,000,000,000 bytes.

Monthly values are 30 days at steady-state run rate. Horizon values total the selected launch simulation, including its ramp, so the two answer different planning questions.

Concurrency and peak

Estimate how many jobs and HTTP requests remain in flight at normal and peak throughput.

The Little’s Law intuition

At a fixed jobs/minute rate, higher latency means each job occupies a slot longer, so more jobs overlap. Average sizing uses mean latency; peak sizing uses P95 latency and the explicit peak override when present, otherwise the multiplier.

Job and HTTP concurrency are calculated independently because a whole job can contain multiple requests and the two latency measurements are not interchangeable.

Workers

Compare modeled demand with aggregate process-local job slots, admission throughput, and HTTP egress capacity.

Why worker recommendations can disagree

Each constraint asks a different question: can workers hold enough simultaneous jobs, admit enough logical jobs/minute, and emit enough retry-adjusted HTTP requests/minute? The recommendation uses the largest computable worker requirement.

A sufficient throughput target does not guarantee sufficient concurrency. Slow jobs can require more worker slots even when the jobs/minute ceiling looks adequate.

Model boundary: the worker recommendation uses steady-state average concurrency and steady request rates. Peak jobs in flight are reported in the preceding section for a separate burst-capacity decision; they are not folded into this recommendation.

Static proxies

Size the configured static pool against its most demanding per-proxy constraint and an operational safety margin.

Why theoretical and recommended counts differ

The binding constraint is whichever of job concurrency, HTTP RPM, or monthly bandwidth needs the most proxies. The theoretical count rounds that raw demand up to a whole proxy. The recommended count first adds safety margin, then rounds up.

3.72 raw proxies → 4 theoretical → 5 recommended with 20% margin

The recommendation depends on modeled workload and supplied or measured proxy limits; it is not an unconditional guarantee of provider behavior.

Model boundary: proxy sizing uses steady-state average job concurrency. The configured maximum concurrency/proxy sizes the pool; measured earned concurrency is diagnostic and can raise a finding, but does not replace that limit. A blank RPM or bandwidth limit may mean either “not applicable” or “not measured,” so check its provenance.
